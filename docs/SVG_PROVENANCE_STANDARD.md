# SVG provenance and technology labels

Every instructional SVG must identify itself inside the artwork, not only in its Markdown caption. Readers should be able to open or download an SVG and still answer: **What is this? What produced it? Which Workshop technology does it actually use? Is it evidence of runtime behavior or a conceptual proposal?**

## Required visible label

Place a compact, legible provenance strip along the lower edge of the viewBox. The label must not obscure the main diagram and must remain visible when the SVG is opened by itself.

Use these fields, in this order:

- **ARTIFACT** — short identifying name or purpose.
- **EVIDENCE** — one of `RUNTIME OUTPUT`, `GENERATED FROM IMPLEMENTATION`, `CONCEPTUAL MAP`, `RESEARCH MODEL`, or `DECORATIVE ASSET`.
- **TECHNOLOGY** — name the technology that actually authored or generated it.
- **WORKSHOP TECHNOLOGY** — name the real package(s) whose code/data it uses, or say `NONE — NATIVE SVG`.
- **GUI.SVG** — `USED` only when the artifact was actually produced through TheSingularityWorkshop.GUI.SVG; otherwise `NOT USED`.

Do not treat the presence of SVG markup, SVG animation, or a Workshop-themed design as use of GUI.SVG. GUI.SVG is a real semantic-to-vector manifestation technology; its use must be evidenced by a generator that invokes that package. Until such a generator is wired in, handcrafted diagrams must say `GUI.SVG: NOT USED`, not imply otherwise.

## Evidence categories

| Label | Meaning |
|---|---|
| `RUNTIME OUTPUT` | The SVG depicts values captured from a running implementation, with the generator, fixture inputs, and sample counts documented. |
| `GENERATED FROM IMPLEMENTATION` | A reproducible generator calls the real code and serializes its outputs. This is not necessarily a live runtime capture. |
| `CONCEPTUAL MAP` | Explains relationships, architecture, or a target design; it does not prove the behavior exists. |
| `RESEARCH MODEL` | Illustrates an exploratory equation or candidate model that is not part of the current runtime contract. |
| `DECORATIVE ASSET` | Dividers, logos, and purely ornamental artwork. Decorative assets are exempt from a large visible footer; retain a meaningful SVG title/description or metadata when appropriate. |

## Generated-artifact rule

Do not hand-edit a generated SVG snapshot without updating its generator and regenerating the snapshot. The provenance label belongs in the generator output so the next CI run does not erase it or report unexplained drift. If the generator is not yet label-aware, track that as unfinished work rather than silently changing the snapshot.

## Accessibility and validation

- Keep `<title>` and `<desc>` meaningful and connected with `aria-labelledby`.
- Use text, not color alone, to distinguish evidence and technology status.
- Keep the label readable at normal document scale and avoid covering content.
- Respect `prefers-reduced-motion` for animated SVGs.
- Parse every SVG as XML in CI. XML validity is not proof of correct provenance, accessible design, correct visual composition, or runtime truth.

## Current label rollout

The three newly added theory diagrams have visible labels stating that they are conceptual maps, native SVG, not generated by GUI.SVG, and not runtime output. This is the honest current state—not a claim that GUI.SVG has already been integrated into the Gestures diagram pipeline. Remaining instructional and generated SVGs must be audited and labelled according to their actual provenance, with generated outputs changed at their source generators.
